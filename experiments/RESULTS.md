> 실험 브랜치 `experiment/bundle-variants` 의 결과를 main 에 합쳤다(2026-10-01). 아래 §7 후보는 **모두 운영 코드에 반영**했다(§10). 코드는 `experiments/lab/`, 측정은 `experiments/bench.py`,
> 서비스 실측(DB 포함)은 `idd-tools/live/overhead_bench.py`, 끝에서 끝까지 정합성은 `idd-tools/live/download_e2e.py`.

## 0. 결론 먼저

| # | 결론 | 근거 |
|---|---|---|
| 1 | **기본은 지금의 "임시 파일 없이 만들면서 보내는 zip"을 유지한다** | 첫 바이트 ≤ 5ms · 서버 메모리가 묶음 크기와 무관(450MB 묶음에서 RSS 증가 0) · 완성본을 먼저 만드는 방식보다 느리지 않다(§3) |
| 2 | **병목은 전송이 아니라 DEFLATE 압축이다** | 같은 480MB 에서 압축 안 한 zip 0.11s ↔ 전부 압축 6.6s(60배). 서버 CPU 가 GB 당 0.17s ↔ 13s(§3) |
| 3 | **압축을 건너뛸 형식을 넓히면(확장자 + 앞부분 시험 압축) 사무 문서가 섞인 묶음의 CPU 가 4배 준다** | pdf · docx · hwp 가 섞인 300파일 묶음: CPU 0.45s → 0.17s(`ext`) · 0.09s(`smart` + 레벨 1)(§3) |
| 4 | **압축 레벨은 정책 결정이다** | 텍스트 120MB: 레벨 1 은 CPU 3배 절약, 크기 +45% · 레벨 9 는 CPU 5배 더 들고 크기 −9%(§3). 사내망이면 1~3 이 합리적이다 |
| 5 | **감사 기록을 낱개로 넣으면 묶음의 첫 바이트가 늦다 → 고쳤다** | 고른 자산 60건: 첫 바이트 0.65s → 0.075s. 원격 DB 왕복 60번이 한 번으로(§5, main 작업 트리에 반영) |
| 6 | **파일마다 요청하는 방식(브라우저 zip)은 이 환경에서 요청 오버헤드가 크다** | 파일당 37ms(차례로) · 8ms(동시 8) ↔ 서버 묶음 1.7ms. 300파일이면 11s ↔ 0.5s(§5) |
| 7 | **저장소 지연이 크면 "여러 조각 동시 읽기"가 효과적이다(7배) — 실저장소로 확인 필요** | 조각당 5ms 모사: 한 파일 안 8조각 동시 읽기 3.37s → 0.44s · 작은 파일 8개 동시 읽기 4.8s → 0.65s(§4) |
| 8 | 서버 스택(httptools · uvloop) · 조각 미리 읽기 · tar 는 바꿀 이유가 없다 | 차이 ±5% 이내(§6) |

## 2. 단건 원본 보내기 (120MB 1개)

| 방식 | 1개 MB/s | 동시 8 MB/s | 서버 CPU(s/GB) |
|---|---:|---:|---:|
| custom1m (현행) | 4,353 | 9,248 | 0.15 |
| anyio1m | 4,439 | 9,226 | 0.14 |
| custom64k | 828 | 1,639 | 0.64 |
| fileresponse (Starlette, 64KiB) | 828 | 1,678 | 0.63 |

→ 조각 크기가 전부다. 1MiB 는 64KiB 보다 5배 빠르고 CPU 는 1/4. 비동기 읽기와 스레드풀 읽기는 같다. **현행 유지.**

## 3. 묶음 (서버가 만들면서 보내기)

첫 바이트는 모든 방식에서 1~5ms 였다(= 만들면서 보내기의 성질). 표는 **총 시간(s) · 서버 CPU(s) · 산출물(MB)**, 동시 1.

| 방식 | small_mixed 59MB | large_media 480MB | text_heavy 120MB |
|---|---|---|---|
| main(현행) | 0.48 · 0.45 · 48.5 | 0.12 · 0.09 · 503 | 1.33 · 1.31 · 20.4 |
| auto 레벨 1 | 0.39 · 0.37 · 49.2 | 0.11 · 0.09 · 503 | **0.50 · 0.48 · 29.6** |
| auto 레벨 3 | 0.41 · 0.38 · 48.8 | 0.11 · 0.09 · 503 | 0.68 · 0.67 · 24.0 |
| auto 레벨 9 | 0.79 · 0.76 · 48.4 | 0.11 · 0.09 · 503 | 5.7 · 5.67 · 18.6 |
| **ext (확장자 확대)** | **0.17 · 0.14 · 48.5** | 0.11 · 0.09 · 503 | 1.37 · 1.36 · 20.4 |
| **smart 레벨 6** | 0.19 · 0.17 · 48.5 | 0.11 · 0.09 · 503 | 1.40 · 1.39 · 20.4 |
| **smart 레벨 1** | **0.11 · 0.09 · 49.2** | 0.11 · 0.09 · 503 | 0.49 · 0.48 · 29.6 |
| stored(전부 무압축) | 0.06 · 0.04 · 57.1 | 0.11 · 0.09 · 503 | 0.05 · 0.04 · 125.8 |
| deflate 전부(L6) | 0.71 · 0.68 · 48.5 | **6.6 · 6.54 · 503.5** | 1.44 · 1.41 · 20.4 |
| auto + 조각 미리 읽기 4 | 0.49 · 0.47 · 48.5 | 0.09 · 0.09 · 503 | 1.44 · 1.43 · 20.4 |
| tar | 0.08 · 0.05 · 57.6 | 0.10 · 0.07 · 503 | 0.04 · 0.03 · 125.9 |

- **압축이 비용의 전부다.** 영상(480MB)은 현행도 무압축이라 0.12s 인데, 영상을 압축해 보내면 6.6s · 산출물은 오히려 커진다(503.5MB).
- **`auto` 의 확장자 목록에는 pdf · docx · xlsx · pptx · hwp 가 없다** → 이미 압축된 파일을 또 압축한다. `ext`(목록 확대)로 small_mixed 가 0.48 → 0.17s.
  목록에 없는 형식(hwp · 암호화 파일)은 `smart` 가 앞 64KiB 를 레벨 1 로 시험 압축해 92% 이상 남으면 무압축으로 담는다 — 추가 CPU 는 파일당 64KiB 시험 1회.
- 압축 레벨: 텍스트에서 L1 → CPU 1/3, 크기 +45%. L9 → CPU 5배, 크기 −9%. **레벨은 "서버 CPU 대 전송 크기" 교환이라 정책으로 정한다.**
  ⚠️ 파이썬 `zipfile` 은 `ZipInfo` 를 직접 넘기면 `ZipFile(compresslevel=)` 을 무시한다(이 실험의 첫 측정이 그래서 무효였다) — 레벨을 쓰려면 `info._compresslevel` 을 줘야 한다.
- 동시 8 요청(압축 있는 묶음): small_mixed main 0.88s · CPU 5.2 ↔ smart L1 0.39s · CPU 1.1. text_heavy 는 L6 2.3s · CPU 17 ↔ L1 0.72s · CPU 5.3.
  서버 CPU 가 요청 수에 선형이라, 압축이 있는 묶음 동시 N 개 = 코어 N 개를 쓴다(스레드풀 10개가 CPU 를 다 먹는다) — 동시 묶음 수 제한(TODO 의 게이트)의 근거가 된다.
- 조각 크기: 64KiB 861 · 256KiB 2,518 · 1MiB 4,001 · 4MiB 4,802 MB/s (RSS +17MB). 1MiB 유지 — 네트워크가 병목이면 4MiB 의 이득은 사라진다.
- tar: 무압축 zip 과 같은 속도 — 이점이 없고 윈도우 기본 도구로 못 연다. 채택하지 않는다.

## 4. 저장소 지연 모사 (조각 읽을 때마다 5ms)

원격 저장소(NFS · 객체)는 로컬 캐시 파일과 달리 읽기마다 지연이 있다. 로컬에서 보이지 않는 효과를 보려고 조각마다 5ms 를 일부러 기다리게 했다.

| 데이터 | 방식 | 총 시간(s) |
|---|---|---:|
| large_media 480MB (파일 4개) | 현행(직렬 읽기) | 3.37 |
| | 한 파일 안 조각 미리 읽기(2 · 8) | 3.07 |
| | 파일 4개 앞서 읽기 | 2.98 |
| | **한 파일 안 4조각 동시 읽기(pread 창)** | **0.86** |
| | **한 파일 안 8조각 동시 읽기** | **0.44** |
| small_mixed 300파일 | 현행 | 4.80 |
| | 조각 미리 읽기 4 | 3.88 |
| | **파일 4개 앞서 읽기** | **0.90** |
| | **파일 8개 앞서 읽기** | **0.65** |

→ 지연이 지배할 때: **큰 파일은 한 파일 안에서 조각을 동시에 읽고, 작은 파일은 여러 파일을 앞서 읽는다.** 단순 "다음 조각 미리 읽기"는 효과가 거의 없다(읽기 스레드 하나가 여전히 직렬이다).
메모리는 `창 크기 × 조각 크기`(8 × 1MiB = 8MiB/요청). **실제 사내 저장소의 지연을 모르므로(마운트 정보 필요) 채택 여부는 실측 뒤에 정한다.**

## 5. 파일마다 요청하는 방식 vs 서버 묶음 — 실서비스(원격 DB · 감사 포함)

작은 파일 60개(100KB). `overhead_bench.py`.

| 방식 | 총 시간(s) | 파일당(ms) |
|---|---:|---:|
| 단건 다운로드 차례로 60번(연결 재사용) | 2.24 | 37.4 |
| 단건 동시 4 | 0.72 | 11.9 |
| 단건 동시 8 | 0.48 | 8.0 |
| **고른 자산 묶음 1번(수정 뒤)** | **0.10** (첫 바이트 0.075) | **1.7** |
| (고르기 전) 고른 자산 묶음 1번 | 0.69 (첫 바이트 0.65) | 11.4 |

- 파일마다 요청하면 요청마다 DB 조회(노출 대상 · 경로)와 감사 한 행이 따른다 — 원격 DB 에서 파일당 ≈ 8ms(동시) ~ 37ms(차례로). 300파일이면 차례로 11s, 동시 8 로도 2.4s.
- **묶음 첫 바이트가 0.65s 였던 원인**: 담길 자산마다 감사 INSERT 를 하나씩 보냈다(60번 왕복). `executemany` 로 한 번에 보내게 고쳐 0.075s 가 됐다(`record_access_many` · 테스트 2건 · main 작업 트리에 반영).
- 브라우저형(client-zip, Node 로 모사) 총 시간은 small_mixed 0.23s(병렬 4) · large_media 1.07s · text_heavy 0.33s — 클라이언트의 CRC-32 계산이 ≈ 470MB/s 상한이다. 사내망(≤ 1Gbps ≈ 125MB/s)이면 병목이 못 된다. **오히려 병목은 요청 수 × DB 지연이다.**
  브라우저형이 서버에 주는 것은 CPU 절약(압축을 클라이언트가 한다)이지만, 위 표처럼 요청 · 감사 비용이 커진다. HTTPS · Chrome/Edge 한정 · 이어받기 난점은 그대로(기록: `bundle_stream.py` 머리말).

## 6. 그 밖의 방식

| 방식 | 결과 | 판단 |
|---|---|---|
| 작업형(완성본을 디스크에 만든 뒤 `Range` 로) | 준비 시간 = 압축 시간(small 0.53s · 480MB 0.12s · text 1.41s) → 받기는 빠름(480MB 0.58s)·**이어받기 가능(앞 40% 뒤 `Range` 로 이어 붙여 바이트 일치)** · 디스크 = 산출물 크기 | 첫 바이트가 준비 시간만큼 늦다. **이어받기 · 진행률이 요구될 때만** 의미 있다 |
| 서버 구성(h11/httptools × asyncio/uvloop) | 단건 8동시 8.2~9.7GB/s · 묶음 0.83~0.99s — 차이 ±10%(잡음 수준) | 바꾸지 않는다(`uvicorn[standard]` 불필요) |
| tar | §3 | 채택 안 함 |

## 9. 프로세스 분리 — 묶음 부하가 화면 응답을 늦추는가 (2026-10-01)

같은 코드를 둘로 띄우고(`PORTAL_ROLE=files uvicorn service.api:app --port …`) 앞단(인그레스)이 경로로 나눠 보낸다. 라우트 코드는 옮기지 않았다(등록할 때 거름) · 테스트 6건(겹치지 않고 합치면 종전 전부).

해석 (과장하지 않는다):
- **화면 요청 지연은 분리하면 덜 흔들린다.** K=8 에서 상세 p95 277 → 162ms · 태그 p95 110 → 45ms · 최대값도 작다. K=16 에서 태그 p50 54 → 26ms(분리는 부하 없음의 21 과 거의 같다).
- **묶음 처리량은 같다**(9.5 vs 9.6/초) — 분리해도 손해가 없다.
- **차이가 크지는 않다.** 이 장비는 10코어라 묶음 8~16개가 CPU 를 다 먹지는 않고, 압축(zlib)이 GIL 을 놓아서 한 프로세스에서도 검색이 아주 막히지는 않는다. 기준 단계의 흔들림(원격 DB · 검색 엔진)이 ±30% 라
  작은 차이는 잡음일 수 있다. **CPU 한도가 작은 파드(2~4코어) · 파일 요청이 더 많은 환경에서는 차이가 커질 것으로 예상하지만 이 실험으로 확인하지는 못했다**(맥에서 코어 수를 제한할 수 없었다).
- **files 의 DB 풀(= 스레드 상한)을 4 로 조이면 오히려 나쁘다**: 묶음 처리량이 절반(5.2/초)이 되고 화면 쪽 꼬리도 좋아지지 않았다. 풀은 기본값으로 둔다. 파일 프로세스의 CPU 상한은 풀이 아니라 **파드의 CPU limit** 으로 건다.
- 분리의 진짜 이득은 지연 평균보다 **운영 격리**다: 파일 프로세스만 따로 늘리고(HPA) · CPU/메모리 한도를 따로 걸고 · 재시작해도 검색 화면이 영향받지 않고 · 느린 요청 로그가 섞이지 않는다.

비용: 배포 파일 · 인그레스 규칙 하나씩 늘고, 개발 환경은 포트가 둘이며(Vite 프록시 규칙 추가), JWT 서명 키 · CORS 설정을 두 프로세스가 같게 가져야 한다. 두 프로세스의 DB 풀 합이 PostgreSQL `max_connections` 안이어야 한다.

## 10. main 반영 결과 (2026-10-01)

실험 브랜치의 결과를 모두 main 에 합쳤다. 운영 코드에 들어간 것과 들어가지 않은 것:
